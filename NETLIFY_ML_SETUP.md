# TERRAX / GeoIntelligence: Netlify + ML API deployment

This setup keeps the website on Netlify and runs the existing Python/FastAPI geospatial service as a separate web service. Netlify serves the Vite/React site and runs the existing Express API as a Netlify Function; the Express API forwards approved analysis requests to FastAPI. No changes are made to the existing `manus.space` deployment by these files.

```text
Browser → Netlify static site → /api/* Netlify Function (Express)
                                  ↓ server-side ML_SERVICE_URL
                             FastAPI geospatial service
```

The current repository provides provider-backed and deterministic geospatial/statistical analysis. It does not include trained model weights or claim a trained AI prediction model. Automatic mineral and petroleum scores are withheld until suitable evidence and independent validation exist.

## 1. Deploy the ML service

1. Put this project source in a GitHub repository that you control. Keep `.env`, `.venv`, `node_modules`, and secrets out of Git.
2. In Render, create a new Blueprint and select that repository. The included `render.yaml` defines a Python web service rooted at `geo-ml-service` with `/health` as its health check. It binds to Render's assigned `$PORT` and uses Python 3.12.8.
3. Wait for the service to deploy, then copy its actual HTTPS service URL. Verify that `<service-url>/health` returns JSON with `status: "ok"`. The service URL is generated by Render; do not guess it.

The Blueprint uses Render's Free plan for a no-charge demo. Render says Free web services spin down after 15 minutes without inbound traffic and can take about a minute to start again; Render also advises against Free instances for production. Because Netlify synchronous Functions have a 60-second execution limit, a cold ML service can occasionally make the first request time out. For dependable interactive usage, use an always-on ML service plan or another host with enough memory and predictable cold starts. See [Render free-service limitations](https://render.com/docs/free) and [Netlify function limits](https://docs.netlify.com/build/functions/configuration/).

## 2. Deploy the website and API gateway to Netlify

Do **not** use Netlify's static drag-and-drop upload of `frontend/dist` for this full setup. That upload does not build this repository's Express Function. Use Git-based deployment or Netlify CLI so the function source is built together with the site, as described in [Netlify's Express guide](https://docs.netlify.com/build/frameworks/framework-setup-guides/express/) and [Vite guide](https://docs.netlify.com/build/frameworks/framework-setup-guides/vite/).

For Git-based deployment, create a new Netlify site from the repository. Configure:

- Base directory: repository root
- Build command: `npm run build`
- Publish directory: `frontend/dist`
- Functions directory: `netlify/functions`
- Node.js build/runtime version: 20

The checked-in `netlify.toml` already declares these settings, the `/api/*` rewrite, and the SPA fallback. Netlify's build detects that configuration automatically.

Alternatively, from the project root, install dependencies and use Netlify CLI:

```bash
npm ci
npx netlify-cli login
npx netlify-cli init
npx netlify-cli deploy --build --prod
```

Follow the CLI prompts to link/create the Netlify site. Keep the project's root as the deployment base. Netlify functions are bundled from source during the build; the ZIP is source code, not a prebuilt functions bundle.

## 3. Connect Netlify to the ML service

In the Netlify site's environment-variable settings, add:

```text
ML_SERVICE_URL = https://<your-actual-render-service>.onrender.com
```

Use the exact HTTPS URL Render assigned, with no `/health` suffix. This variable is used only by the Netlify Function; do not create a `VITE_ML_SERVICE_URL` variable or expose the backend URL in browser code. `VITE_API_BASE_URL` can remain unset because production requests use the same-origin `/api` route. The frontend still defaults to `http://localhost:5000` during local Vite development.

After saving the variable, redeploy the Netlify site so the Function runtime receives it. No PostgreSQL database is required for the described map, weather, indicators, or analysis flow. Do not set `DATABASE_URL` unless you have separately provisioned and configured a real database.

## 4. Smoke-check the deployed flow

After both services are live, open these URLs, replacing the Netlify site URL with the one Netlify assigned:

- `https://<your-site>.netlify.app/api/health` should return an `ok` Express health response and report `dependencies.ml_service` as `available`.
- `https://<your-render-service>.onrender.com/health` should return FastAPI `status: "ok"`.
- On the site, search a place or click the map and run the weather analysis. Then try the region analysis panel. A provider outage or missing evidence should be shown as unavailable/insufficient, not filled with fabricated values.

If health reports the ML service as unavailable, check the Netlify `ML_SERVICE_URL`, Render deploy logs, and whether the Render Free service is waking from idle. Redeploy Netlify after changing runtime environment variables.

## Limits to know

Netlify Functions are request-scoped and have a 60-second synchronous execution limit. This repository's long provider-discovery proxy timeout is reduced to 50 seconds when running on Netlify. The FastAPI service's raster upload/preprocessing routes are not exposed through the Express `/api` proxy and large binary uploads should not be routed through the standard buffered Netlify Function. Deploy the Python service directly for those operations. The weather and JSON-based analysis API routes are the intended Netlify path.
